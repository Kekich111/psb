## 1. Что мы выяснили из данных

### 1.1 База знаний (по скриншотам и загруженным файлам)
- ~21 файл. Два класса, класс зашит в имя файла:
  - `документы компании__<тип> ...` — 8 файлов: 3 договора, доп. соглашение, письмо, **2 редакции** регламента, служебная записка. Размер мизерный (≈32 КБ байт, то есть порядка 6–8 тыс. токенов **на всё**).
  - `законы__<акт>_ст<N>_действующая` — ~13 файлов, по одной статье: 152-ФЗ ст.9, КоАП 13.11, МРОТ ст.1, НК (112, 114, 145, 164, 224, 284), ТК (59, 70, 99, 152). Почти весь объём даёт НК ст.164 и ст.284 (140 и 169 КБ).
- **Вывод 1:** корпус документов компании целиком влезает в контекст. Задача по ним — не «найти», а «выбрать верный документ и редакцию и не перепутать контрагента». Retrieval нужен главным образом для законов (особенно двух больших статей НК).
- «Мы / наш» в вопросах = ООО «Меридиан» (арендатор и покупатель в договорах, адресат регламентов). Определять **из данных** (самая частая сторона в документах компании), не хардкодить.

### 1.2 Формат законов
Файл закона = шапка + текст:
```
Источник: Статья 59. ТК РФ ... / URL / Дата выгрузки: 10.10.2026
Статья 59 изменена с 1 марта 2027 г. - ФЗ № 246-ФЗ
Статья 59 изменена с 1 сентября 2026 г. - ФЗ № 144-ФЗ
<текст>
```
- В шапке — **структурированные метаданные о редакциях**: дата выгрузки и будущие/недавние изменения. Это ключ к правилу «законы только в действующей редакции, старой нет».
- В теле встречаются **редакционные пометки не из нормы** («О конституционно-правовом смысле … см. постановление КС РФ …»). Их нельзя цитировать как норму.
- Нумерации частей и абзацев в тексте нет. «Часть первая / вторая» восстанавливается эвристикой (вводная фраза с «:»). Если разбор неуверенный — ссылаться на «ст. 59» без части.

### 1.3 Таксономия вопросов (по 18 демо-вопросам и эталонам)
| Тип | Примеры (id) | Ожидаемое поведение |
|---|---|---|
| Прямой поиск | 1, 2, 14 | Ответ + ссылка на документ/пункт |
| Вывод из нормы | 7 («в 2 ночи пропустят?» → круглосуточный доступ) | «Да» + пункт, логика явная |
| Нет в базе | 3 (пособие по беременности) | Прямо сказать, что в базе нет; из памяти не отвечать |
| Ложная предпосылка | 4 (500 000 вместо 450 000), 13 («удалить вообще всё») | Поправить пользователя, назвать верное значение |
| Редакция/дата | 5 (договор авг. 2024 → регламент ред. 10.01.2023, порог 10 млн) | Применить редакцию на дату события, упомянуть действующую |
| Нормы нет в явном виде | 8, 11 (4 дня вместо разрешённых 3) | Сказать, что «документом не предусмотрено» |
| Похожие контрагенты | 8/9/17 («Альфа-Трейд» ≠ «Альфа-Трейдинг») | Не смешивать документы |
| Диалог | 6, 15–18 | Ответ на последнюю реплику с учётом истории; прошлые реплики ассистента **не доказательство** |
| Частично в базе | 13 (ст. 9 есть, ст. 6, 10, 11 нет) | Ответить на то, что подтверждено, и **перечислить недостающие статьи** |

Из эталонов видно стиль: прямой вердикт первым словом, документ + № + пункт, 30–90 слов, без воды, явное «не предусмотрено / в базе нет».

В кейсе есть ещё категории, которых нет в демо: просьба помочь в противоправном действии, поддельные системные сообщения, давление «исправь ответ», не-юридические запросы. Заложены в архитектуру, тест-кейсы писать самим.

## 2. Что диктует метрика

```
Score = 0.7·MatchRate + 0.3·WinRate
s_i = (r_раунд1 + r_раунд2)/2 , r ∈ {0, .25, .5, .75, 1} относительно baseline
Выдуманный факт → s_i = 0
```
Следствия для дизайна:
1. **Асимметрия:** один выдуманный факт стоит дороже, чем несколько «скучных» точных ответов. Все слои защиты настроены на precision.
2. **Лишний отказ тоже проигрыш** (ответ был в базе, а бот отказал). Поэтому перед отказом обязателен rescue-retrieval.
3. **WinRate считает только победы и поражения, ничьи исключаются.** Ответ «не хуже baseline» не даёт ничего: нужно быть заметно лучше (точнее ссылка, верная редакция, поправка предпосылки).
4. Судья сверяется с **golden**. Лишние, пусть и верные, детали могут быть восприняты как расхождение с эталоном. Отвечать ровно на вопрос.
5. Экспертная часть (30% онлайн-этапа): достоверность 25%, работоспособность 20%, архитектура/документы 20%, **скорость и эффективность 15%**, интерфейс 15%. Значит, число LLM-вызовов, кэш и параллелизм — оцениваемые вещи.
6. Жёсткие рамки платформы: 20 минут, 8 CPU/16 ГБ, 5 сабмитов в день, только разрешённые библиотеки, **только корневые `.py`**, нет `pip install`, нет внешних источников.

## 3. Варианты и решение (ADR-001)

| | Вариант | Плюсы | Минусы |
|---|---|---|---|
| A | Классический RAG: гибридный поиск → rerank → один промпт | Быстро, просто | Не решает редакции, двойников контрагентов, предпосылки. Ожидаемо около baseline |
| B | **Staged pipeline**: анализ → детерминированный retrieval → reason/compose → guard/verify → render | Предсказуемо по времени, каждый слой тестируется, контрактные границы | Нужна дисциплина с контрактами |
| C | Агентный цикл с tool-calling (search, open_doc, list_editions) | Гибко | DeepSeek Flash + 20 минут + нестабильность. Трудно воспроизвести и отлаживать |
| D | Весь корпус в контекст | Нулевой retrieval-miss | Законы НК ≈ десятки тысяч токенов, дорого и шумно; не масштабируется |

**Решение: B+** — вариант B с тремя усилениями:
1. **Tiered context.** Если корпус документов компании ≤ `COMPANY_FULLCTX_TOKENS` (по умолчанию 12k) — в контекст кладутся **все** документы компании (в компактном виде, с метками редакции). Retrieval работает только по законам. Если корпус вырастет — автоматический откат на полноценный retrieval по всему.
2. **Document Cards + Edition Graph** (структурированный слой поверх текста) — решает редакции, допсоглашения, двойников.
3. **Один ограниченный второй hop** (только по запросу reasoner'а) вместо свободного агентного цикла.

Отвергнуто осознанно: C (риск таймаута и недетерминизма), чистый D.

## 4. Целевая архитектура

```
                      ┌──────────────── OFFLINE / при старте (кэш по sha256 KB) ───────────────┐
 knowledge-base.zip → │ S0 Ingest → S1 Cards+EditionGraph → S2 Chunk → S3 Index(BM25+bge-m3)    │
                      └──────────────────────────────────┬────────────────────────────────────┘
                                                         ▼  KnowledgeBase (контракт)
 вопрос / история ─► S4 Analyze ─► S5 Retrieve ─► S6 Reason+Compose ─► S7 Guard+Verify ─► S8 Render ─► ответ
                      (LLM #1)     (код+embed+      (LLM #2, JSON)       (код + LLM #3     (код)
                                    rerank)                               по условию)
                                        ▲                │ need_more (≤1 раз)
                                        └────────────────┘
                                                 │ NO_DATA → rescue-retrieval → повторный S6
```

### S0 Ingest
- Чтение zip (txt/md/docx). Класс документа по префиксу имени. Парсинг шапки закона: `Источник`, `URL`, `Дата выгрузки`, строки «изменена с …».
- Редакционные пометки помечаются `is_editorial=True` и не попадают в citable-текст.

### S1 Cards + Edition Graph
- На каждый документ компании — **одна LLM-экстракция** в `DocCard`: тип, номер, дата, стороны (с ИНН), предмет, `effective_from`, `supersedes`, `amends` (какой договор, какие пункты, с какой даты).
- **Валидация карточки кодом:** номер, даты, суммы и названия сторон обязаны находиться в тексте документа. Иначе поле → `None`.
- Edition Graph: документы одной «семьи» (редакции регламента; договор + допсоглашения) связываются. Функция `resolve(family, as_of_date) -> [Edition, status]`.
- Допсоглашения **не переписывают** текст договора. Это overlay: пункт базового договора плюс пометка «изменён ДС № … с даты …». В evidence оба варианта подаются с метками, решает reasoner по дате.
- Реестр сторон: точные названия, ИНН, номера договоров, `confusable_with` (rapidfuzz высокий, но названия разные: «Альфа-Трейд» / «Альфа-Трейдинг»). Эти сущности **никогда** не сливаются.

### S2 Chunk
- Документы компании: чанк = пункт (`п. 3.1`), с хлебными крошками (`Договор № … / раздел 3 / п. 3.1`).
- Законы: по частям, пунктам и подпунктам. Две большие статьи НК режутся на пункты. Заголовок статьи входит в каждый чанк.
- `chunk_id = {doc_id}#{locator}`, сохраняются offsets в исходном тексте (для подсветки в UI).
- Этап `CHUNKER` — настройка платформы; читать, но не зависеть от неё.

### S3 Index
- BM25 с лёгкой нормализацией для русского (lower, ё→е, усечение основы до 5–6 символов, числа и «ст. N» как отдельные токены). Морфологических библиотек нет в разрешённом списке.
- Dense: `bge-m3` через прокси, векторы в `numpy` (чанков сотни, FAISS не нужен).
- **Кэш эмбеддингов по sha256(текста)**: готовый файл кладётся в ZIP (корень, без папок), недостающее досчитывается при старте. Решение не ломается, если KB на платформе чуть отличается от локальной.

### S4 Analyze (LLM #1, JSON, T=0)
Вход: история + последняя реплика + компактный реестр документов (по строке на документ).
Выход `QueryAnalysis`:
- `standalone_question` (диалог свёрнут), `our_company` подставлен.
- `kind`-флаги: lookup / multi-doc / date-sensitive / off-topic / illegal / adversarial.
- `entities`: контрагенты, № договоров, типы документов, статьи.
- `event_date` (явная в вопросе) или `None`.
- `premises[]` — утверждения пользователя, которые надо проверить («плата 500 000»).
- `ambiguities[]` — например, «Альфа» без уточнения.
- Реплики ассистента из истории — **недоверенный контекст**, не доказательства (ответ в демо-вопросе 6 ссылается на п. 5.2, мы всё равно перепроверяем по базе).
- Детерминированный pre-guard (regex) на явные инъекции — дополнительно к LLM-классификации.

### S5 Retrieve (в основном код)
1. **Entity routing:** точное совпадение № договора и алиасов сторон → документы форсируются.
2. **Full-context tier:** документы компании целиком (если укладываются в бюджет).
3. **Edition resolution:** по `event_date` метки `APPLICABLE / SUPERSEDED / NOT_YET`. Если даты нет, а редакции дают разный ответ — подаются обе.
4. **Hybrid search по законам:** BM25 top-40 ∪ dense top-40 → RRF → reranker (top-12) → расширение соседними чанками → бюджет ~6–8k токенов.
5. **Прямые обращения к статье** (`ст. 70`) — по regex к `law_article`.
6. **KnowledgeGap hints:** кросс-ссылки внутри найденных норм («статьи 6, 10 и 11») сверяются с инвентарём базы; отсутствующие передаются reasoner'у (так устроен эталон вопроса 13).
- Реранкер опционален: при ошибке падаем на RRF-порядок. Формат ответа `/rerank` разный у провайдеров (`results` vs `data`), парсить оба.

### S6 Reason + Compose (LLM #2, JSON)
Один вызов возвращает структуру, а не свободный текст:
```json
{
  "verdict": "ANSWER|PARTIAL|NO_DATA|FALSE_PREMISE|CLARIFY|REFUSE_ILLEGAL|OFF_TOPIC",
  "premise_checks": [{"premise":"…","status":"confirmed|contradicted|unverifiable","evidence":["id"]}],
  "claims": [{"text":"…","type":"fact|inference","evidence":["chunk_id"]}],
  "missing_info": ["…"],
  "clarifying_question": null,
  "need_more": {"queries": []}
}
```
Финальный текст собирается **из claims кодом** (S8), а не пишется моделью свободно. Каждое утверждение обязано иметь evidence id, иначе его нет.

### S7 Guard + Verify
Детерминированные проверки (всегда, бесплатно):
- G1 все `evidence` ids существуют в EvidencePack.
- G2 **числа, проценты, даты, суммы, № документов** в итоговом тексте ⊆ evidence ∪ вопрос ∪ история пользователя.
- G3 все упомянутые «ст./п./№» существуют в инвентаре базы.
- G4 упомянутые названия документов/организаций ∈ реестр.
- G5 вердикт ANSWER без единой ссылки → понижается до NO_DATA/PARTIAL.
- G6 в ответе нет фрагментов системного промпта.
LLM-критик (`VERIFY_MODE=full`, пропускается в `lite` при чистых G1–G6 и простом вопросе): для каждого claim «следует ли из процитированного?». Не следует → claim удаляется или переписывается один раз. Остались невалидные → понижение до PARTIAL только с подтверждёнными claims.
- **Rescue:** `NO_DATA` при непустом топе поиска → один повторный проход с переформулированными запросами (multi-query) перед финальным отказом.

### S8 Render
- Детерминированная сборка текста в стиле эталонов (раздел 8) + структурированный `AssistantResponse` для UI.
- В CSV уходит одна строка текста (переводы строк допустимы по CSV-экранированию, но лучше компактный абзац).

## 5. Контракты (contract-first)

**Правило:** сначала контракт и фикстуры, потом реализация. Источник истины — `app/core/psb_contracts.py`. Любое изменение контракта = PR только с контрактом + bump `CONTRACT_VERSION` + запись в `contracts/CHANGELOG.md` + обновление фейков. Блоки общаются **только** через эти типы.

```python
# app/core/psb_contracts.py   CONTRACT_VERSION = "1.0.0"
from __future__ import annotations
from datetime import date
from enum import Enum
from typing import Optional, Protocol
from pydantic import BaseModel, Field

# ---------- домен ----------
class DocClass(str, Enum):
    LAW = "law"; COMPANY = "company"

class DocKind(str, Enum):
    LAW="law"; CONTRACT="contract"; AMENDMENT="amendment"
    REGULATION="regulation"; LETTER="letter"; MEMO="memo"; OTHER="other"

class Party(BaseModel):
    name: str; inn: Optional[str] = None; role: Optional[str] = None

class LawAmendmentNote(BaseModel):
    effective_from: date; act: str            # «ФЗ от 26.07.2026 № 246-ФЗ»

class LawMeta(BaseModel):
    act_name: str; article: str
    exported_at: Optional[date]
    amendments: list[LawAmendmentNote] = []

class AmendTarget(BaseModel):
    target_doc_id: Optional[str]; clauses: list[str] = []; effective_from: Optional[date]

class DocCard(BaseModel):
    doc_id: str; file: str; doc_class: DocClass; kind: DocKind
    title: str; number: Optional[str]; doc_date: Optional[date]
    family_id: Optional[str] = None           # редакции одного документа
    effective_from: Optional[date] = None
    effective_to: Optional[date] = None       # None = действует
    parties: list[Party] = []
    amends: list[AmendTarget] = []
    law: Optional[LawMeta] = None
    approx_tokens: int

class Chunk(BaseModel):
    chunk_id: str; doc_id: str
    locator: str                               # «п. 3.1» | «ч. 1» | «ст. 59»
    breadcrumb: str; text: str
    start: int; end: int                       # offsets в исходном файле
    is_editorial: bool = False

class KnowledgeBase(BaseModel):
    kb_hash: str
    cards: dict[str, DocCard]
    chunks: dict[str, Chunk]
    article_inventory: list[str]               # какие статьи/акты есть в базе
    our_company: Optional[str]

# ---------- запрос ----------
class RunMode(str, Enum):
    BATCH = "batch"     # CSV-платформа: нельзя переспрашивать
    CHAT = "chat"       # веб: можно CLARIFY

class Turn(BaseModel):
    role: str; content: str                    # "user" | "assistant"

class ChatRequest(BaseModel):
    history: list[Turn]                        # последняя реплика user — последняя
    mode: RunMode = RunMode.BATCH
    as_of: Optional[date] = None               # «сегодня» для расчётов

class QueryAnalysis(BaseModel):
    standalone_question: str
    kinds: list[str]                           # lookup|multi_doc|date|off_topic|illegal|adversarial
    entities: dict[str, list[str]] = {}
    event_date: Optional[date] = None
    premises: list[str] = []
    ambiguities: list[str] = []
    search_queries: list[str]                  # 1–3 переформулировки для retrieval

# ---------- evidence ----------
class Applicability(str, Enum):
    APPLICABLE="applicable"; SUPERSEDED="superseded"
    NOT_YET="not_yet_in_force"; UNKNOWN="unknown"

class EvidenceItem(BaseModel):
    eid: str                                   # = chunk_id
    chunk: Chunk; card: DocCard
    applicability: Applicability = Applicability.UNKNOWN
    note: Optional[str] = None                 # «ред. от 10.01.2023», «изменён ДС №1 с …»
    score: float = 0.0

class KnowledgeGap(BaseModel):
    description: str                           # «в базе нет ст. 6, 10, 11 152-ФЗ, на них ссылается ст. 9»

class EvidencePack(BaseModel):
    items: list[EvidenceItem]
    gaps: list[KnowledgeGap] = []
    full_context_used: bool = False

# ---------- ответ ----------
class Verdict(str, Enum):
    ANSWER="ANSWER"; PARTIAL="PARTIAL"; NO_DATA="NO_DATA"
    FALSE_PREMISE="FALSE_PREMISE"; CLARIFY="CLARIFY"
    REFUSE_ILLEGAL="REFUSE_ILLEGAL"; OFF_TOPIC="OFF_TOPIC"

class Claim(BaseModel):
    text: str; type: str                       # fact | inference
    evidence: list[str]                        # eids; пусто нельзя для fact

class PremiseCheck(BaseModel):
    premise: str; status: str; evidence: list[str] = []

class Draft(BaseModel):
    verdict: Verdict
    claims: list[Claim] = []
    premise_checks: list[PremiseCheck] = []
    missing_info: list[str] = []
    clarifying_question: Optional[str] = None
    need_more_queries: list[str] = []

class Citation(BaseModel):
    eid: str; doc_id: str; doc_title: str; locator: str
    start: int; end: int; quote: str           # для подсветки в UI

class GuardReport(BaseModel):
    passed: bool; violations: list[str] = []; downgraded_from: Optional[Verdict] = None

class AssistantResponse(BaseModel):
    text: str                                  # финальный текст (в CSV идёт он)
    verdict: Verdict
    citations: list[Citation] = []
    clarifying_question: Optional[str] = None
    guard: GuardReport
    trace: dict = {}                           # тайминги, llm_calls, retrieved ids — для UI и скорости
    contract_version: str = "1.0.0"

# ---------- интерфейсы блоков ----------
class LLM(Protocol):
    def chat(self, messages: list[dict], *, json_mode: bool = False,
             max_tokens: Optional[int] = None) -> str: ...
    def embed(self, texts: list[str]) -> "list[list[float]]": ...
    def rerank(self, query: str, docs: list[str], top_n: int) -> list[int]: ...

class Ingestor(Protocol):
    def build(self, kb_zip_path: str, llm: LLM) -> KnowledgeBase: ...

class Retriever(Protocol):
    def retrieve(self, a: QueryAnalysis, req: ChatRequest) -> EvidencePack: ...

class Analyzer(Protocol):
    def analyze(self, req: ChatRequest, kb: KnowledgeBase) -> QueryAnalysis: ...

class Composer(Protocol):
    def compose(self, a: QueryAnalysis, ev: EvidencePack, req: ChatRequest) -> Draft: ...

class Verifier(Protocol):
    def verify(self, d: Draft, ev: EvidencePack, a: QueryAnalysis) -> tuple[Draft, GuardReport]: ...

class Assistant(Protocol):                     # ЕДИНАЯ точка входа для solution.py и веба
    def answer(self, req: ChatRequest) -> AssistantResponse: ...
```

### Контрактные артефакты
- `contracts/examples/*.json` — по золотому примеру на каждый тип (в том числе по одному на каждую строку таблицы 1.3).
- `app/core/psb_fakes.py` — фейковые реализации каждого протокола, возвращающие фикстуры. Позволяют писать любой блок и UI без остальных.
- `tests/contract/` — тест на блок: «на вход `examples/X.in.json` отдаёт валидный `X.out.json`-тип» + property-тесты инвариантов (раздел 7).

## 6. Правила дат и редакций

`as_of` = «сегодня». Дата события — `event_date`, если она есть в вопросе, иначе `as_of`.

**Документы компании.**
1. Редакция документа берётся по `effective_from ≤ event_date < effective_to`.
2. Допсоглашение применяется, если его `effective_from ≤ event_date`.
3. Нет даты, редакции дают **разный** ответ → в BATCH ответить по действующей и явно упомянуть прежнюю; в CHAT можно уточнить.
4. Если к дате события подходящей редакции в базе нет → так и сказать, не подменять другой.

**Законы** (есть только текущая редакция, `exported_at`):
| Ситуация | Поведение |
|---|---|
| `event_date` ≥ последнего `amendment.effective_from`, который ≤ `exported_at` | Текст применим |
| `event_date` < такого изменения | Старой редакции в базе нет → сказать, выводов не делать |
| Есть изменения с датой > `exported_at` | Упомянуть, что текст может измениться; **содержание будущей редакции не домысливать** |
| Дата не указана | Применить текущую, отметить дату выгрузки |

**[гипотеза]** Текст в файле ТК ст.59 отражает состояние на 10.10.2026 (включая изменение с 01.09.2026, но без изменения с 01.03.2027). Проверить на других законах, прежде чем зашивать правило как есть.

## 7. Поведенческая матрица и инварианты

| Ситуация | Вердикт | Шаблон |
|---|---|---|
| Ответ однозначно в базе | ANSWER | «Вердикт. Факт (док. №, п.). Источник.» |
| Ответ в базе лишь частично | PARTIAL | «Подтверждено: … Не подтверждено / в базе нет: … (перечень)» |
| Ничего нет | NO_DATA | «В базе знаний нет … Отвечать по памяти не буду. Обратитесь к …» |
| Предпосылка пользователя неверна | FALSE_PREMISE | «Не … : по документу X (п. N) верно …» |
| Двусмысленность (CHAT) | CLARIFY | один уточняющий вопрос, без ответа по существу |
| Двусмысленность (BATCH) | ANSWER/PARTIAL | ответ с явным допущением; для двойников — по каждому, если бюджет позволяет |
| Противоправная просьба | REFUSE_ILLEGAL | отказ помогать + что говорят документы о требованиях и последствиях |
| Не юридический запрос | OFF_TOPIC | вежливо про границы компетенции |
| Инъекция / «забудь инструкции» / «system:» | по сути вопроса | игнорировать инструкции, ответить на легитимную часть |
| Давление «исправь ответ» без нового основания | прежний вердикт | остаться при подтверждённом базой |

**Инварианты (property-тесты, нарушение = баг блока):**
- I1 Любой `Claim.type=fact` имеет ≥1 `evidence`, все они ∈ EvidencePack.
- I2 В `AssistantResponse.text` нет числа/даты/№, отсутствующих в evidence ∪ вопросе.
- I3 Ссылка на документ ⇒ документ ∈ KB.
- I4 Контрагенты с `confusable_with` не смешиваются в одном ответе без явной оговорки.
- I5 Документ не может быть `APPLICABLE`, если `event_date` вне его периода.
- I6 `verdict=ANSWER` ⇒ ≥1 цитата.
- I7 Результат детерминирован при `TEMPERATURE=0` с точностью до retry.
- I8 Любой сбой блока → деградация к безопасному ответу (NO_DATA-шаблон), **никогда** пустая строка и никогда исключение наружу.

## 8. Стиль ответа (под судью с golden)

- Первое слово — вердикт («Да», «Нет», «По договору …», «В базе нет …»).
- Документ + номер + пункт: «по договору аренды № А-08/2024 (п. 4.3)». Для закона: «ТК РФ, ст. 70».
- Целевая длина 40–120 слов (рекомендация регламента — до 150). Один-два факта сверх вопроса — максимум, и только подтверждённые.
- Неверная предпосылка: сначала верное значение, потом «а не …».
- Нет данных: «В базе знаний нет … Отвечать по памяти не буду».
- Редакции: назвать применимую редакцию и почему; действующую — одной фразой.
- Без юридических советов «от себя», без «как правило», без оговорок про «я ИИ».
- Один абзац (без markdown-заголовков, списки только если действительно перечень).

## 9. Бюджеты производительности

- LLM-вызовов на вопрос: **минимум 2** (analyze + compose), +1 критик по условию, +1 rescue/второй hop по условию. Эмбеддинг вопроса и rerank — по одному вызову.
- Параллелизм: `MAX_WORKERS` с платформы (в примере по умолчанию 2). Пул потоков, общий rate-limiter, экспоненциальный backoff на 429/5xx, ограниченные retries.
- **Дедлайн-менеджер:** `DEADLINE_SEC` (по умолчанию 15 мин из 20). Оставшееся время → понижение режима: full → lite → «ANSWER без критика» → безопасный шаблон. `submission.csv` пишется атомарно при старте (заглушки) и перезаписывается по мере готовности и в конце.
- Индекс строится один раз на процесс; кэш в `/tmp` по `kb_hash`.
- Токен-бюджеты: analyze ≤ 1.5k вх., compose ≤ 9k вх. и ≤ 700 вых.

## 10. Веб-интерфейс (обязателен для допуска к экспертной оценке)

- Backend: FastAPI (`/api/chat`, SSE-стрим стадий, `/api/doc/{doc_id}`, `/api/health`). Он вызывает **тот же** `Assistant.answer`, что и `solution.py`.
- Frontend: лёгкий (статический SPA без сборочной цепочки либо Vite/React, как решит команда). Один `compose.yaml`, один порт.
- Обязательные элементы: чат с историей; бейдж вердикта (Ответ / Частично / Нет в базе / Неверная предпосылка / Уточнение / Отказ); **панель источников** с подсветкой процитированного фрагмента в полном тексте документа; метка редакции и её применимости; панель «Как получен ответ» (стадии, тайминги, что искали, чего не нашли — аргумент для жюри по критерию достоверности).
- Дополнительно (если успеем): уточняющие вопросы в CHAT-режиме; «план действий» для процедурных вопросов; self-check badge.

## 11. Оценка качества (eval)

Судья скрыт, поэтому свой стенд обязателен.
- **Набор:** 18 демо-кейсов с эталонами + синтетика (~80–120) по каждой категории раздела 1.3 + категории, которых нет в демо (противоправные просьбы, инъекции, давление, off-topic). Синтетику генерируем LLM по документам, **эталоны проверяем руками**.
- **Судья:** локальная копия протокола — парный, два раунда со сменой порядка, шкала 0–1, baseline = `sample_submission` (запускать в том же стенде). Выдуманный факт → 0.
- **Детерминированные метрики:** валидность цитат, числовая заземлённость (I2), доля NO_DATA на ответимых вопросах (over-refusal), доля ответов на неответимые (hallucination), среднее число LLM-вызовов, время на вопрос.
- **Гейт перед сабмитом:** Score не ниже предыдущего более чем на 0.02, fabricated не растёт, I1–I8 зелёные.
- Локально модель может быть любая, но **промпты должны работать на DeepSeek V4.1 Flash**: JSON-режим с толерантным парсером (strip ```json, ремонт, ретрай), игнорирование поля рассуждений, если прокси его отдаёт.
- Журнал сабмитов `SUBMISSIONS.md`: дата, коммит, public-score, что изменилось. Сабмитов 5 в день, тратим осознанно. Public-подмножество не равно private, не переобучаться на лидерборд.

## 12. Блоки, зависимости, Definition of Done

```
 B1 Ingest+Cards+EditionGraph ──┐
 B2 Chunk+Index ────────────────┼─► B3 Retrieve ──┐
 B4 Analyze (prompts) ──────────┘                 ├─► B6 Orchestrator+solution.py ─► B8 Web
 B5 Compose+Guard/Verify+Render ──────────────────┘            ▲
 B7 Eval stand (cases, judge, metrics) ─────────────────────────┘ (мерит всё)
```
| Блок | Вход → выход (контракт) | DoD |
|---|---|---|
| B1 | zip → `KnowledgeBase.cards`, edition graph, реестр | карточки всех демо-документов валидны; `resolve()` покрыт тестами на редакции регламента |
| B2 | `KnowledgeBase` → индекс, кэш эмбеддингов | старт ≤ 60 с на холодном кэше; кэш в zip работает |
| B3 | `QueryAnalysis` → `EvidencePack` | recall@8 на размеченных парах «вопрос → чанк» ≥ целевого; gaps находятся |
| B4 | `ChatRequest` → `QueryAnalysis` | корректный `our_company`, `event_date`, `premises` на демо и синтетике |
| B5 | `QueryAnalysis+EvidencePack` → `Draft` → `AssistantResponse` | I1–I8 зелёные; стиль раздела 8 |
| B6 | всё → CSV | полный `submission.csv` при любых сбоях; дедлайн-менеджер |
| B7 | кейсы → отчёт | воспроизводимый прогон одной командой, парный судья |
| B8 | `AssistantResponse` → UI | основной сценарий проходится в браузере, подсветка цитат |

**Порядок работ:**
1. **M0** (первые часы): заморозка контрактов + фейки + CI-скелет. Параллельно B7 начинает собирать кейсы, B8 рисует UI на фейках.
2. **M1:** сквозной вертикальный срез на тривиальных реализациях (BM25 + один промпт). Первый сабмит платформы: проверяем окружение, формат `/rerank`, реальные переменные, логи.
3. **M2:** B1 и B3 с редакциями и сущностями, B4. Здесь основной прирост.
4. **M3:** B5 guard/verify, rescue, eval-гейты. Второй-третий сабмиты.
5. **M4:** UI-полировка, README/Docker, презентация, оставшиеся сабмиты — на финальный тюнинг.

## 13. Риски

| Риск | Митигация |
|---|---|
| Формат `/rerank` и имя модели расходятся (в примере по умолчанию `cohere/rerank-5-fast`, в регламенте Qwen3 Reranker 8B) | Брать `RERANKER_MODEL` из env, парсить `results`/`data`, при ошибке RRF-порядок |
| В примере KB лежит как `kb.zip`, в регламенте `knowledge-base.zip` | Искать все варианты имён (как в примере) |
| Flash плохо держит JSON | толерантный парсер + 1 ретрай + деградация |
| Таймаут 20 мин | дедлайн-менеджер, атомарные записи CSV, пул с лимитом |
| База на платформе отличается от локальной | никакого хардкода имён и номеров документов; кэш эмбеддингов по хэшу текста |
| Промпт-инъекция внутри документов базы | документы — данные, не инструкции; guard G6 |
| LLM-экстракция карточки ошибается | валидация полей кодом по тексту; поле без подтверждения = None |
| Переобучение на 18 демо-вопросов | синтетический набор, hold-out, смотреть private-прокси метрики |
| Хардкод эталонов | **запрещён** регламентом (логика должна быть реализована и проверяема) |
| Нерешённая эвристика частей/абзацев закона | при неуверенности ссылаться на статью целиком |
